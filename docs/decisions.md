## 2026-07-09 — Environment management overhaul (dev / staging / prod)

**Context:** App has zero live users. Audit found the app's dev/staging/prod wiring was broken in ways that predate any users: every built Android app (including the E2 "QA" APK) read/wrote Firestore against **production**, because `firebaseSetup.ts` picked config via `__DEV__`, which is `false` in any standalone build, not just release ones. Every PR preview on web also served against production Firestore for the same reason. Full original audit: see the Artifact linked in this conversation (not persisted to the repo).

### Decided

- **One explicit signal, everywhere: `EXPO_PUBLIC_APP_ENV`** (`development` \| `staging` \| `production`). Never infer environment from `__DEV__` in a built app again — `__DEV__` only means "running under Metro," nothing else.
  **Why:** the whole bug class existed because environment was *implicit*. Making it one named, explicit value that both `app.config.ts` (Node, build-time) and the client bundle (`EXPO_PUBLIC_*` inlined by Expo's babel preset) read the same way closes it structurally, not just at this one call site.

- **Fail loud, never default to production.** If `EXPO_PUBLIC_APP_ENV` is unset in a built (non-Metro) context, `firebaseSetup.ts` throws at startup instead of silently falling back to the prod config like it did before.
  **Why:** a silent prod default is exactly how this bug shipped originally. Throwing turns "forgot to set the env var" into an immediate crash during QA, not a quiet data-integrity leak discovered later.

- **Firebase config *values* stay as hardcoded objects** (`firebaseConfigDev` / `firebaseConfigProd`), keyed by the env var — not exploded into more `EXPO_PUBLIC_FIREBASE_*` vars.
  **Why:** these values aren't secrets (Firebase web config is safe client-side, scoped by security rules), so more env vars would add indirection across `.env.*` files / `eas.json` / 3 workflows without a security benefit. Only the *selector* needs to be wired everywhere.

- **Staging (E2) shares the `ssr-juniors-dev` Firebase project with local development** — no third Firebase project introduced yet.
  **Why:** zero users means QA/dev data collision is cheap right now. Revisit only once QA data volume makes that collision actually costly (noted as deferred, not forgotten).

- **Branch strategy: adopt `main` as the protected production branch.** `main` was a one-commit local stub (the original `create-expo-app` scaffold) that had never been pushed to GitHub — `develop` was the real trunk (GitHub's default branch, only branch on origin, all real history). Confirmed `main`'s commit was an ancestor of `develop`, so we fast-forwarded local `main` to `develop`'s tip (lossless) and pushed it to origin for the first time.
  **Why:** the original CI had `develop → prod Hosting` and `main → dev Hosting` — backwards from any sane convention, and made worse by `main` not really existing on GitHub. Rather than patch around a dead branch, we made `main` real and gave it the meaning its name implies.
  **Resulting mapping:** `develop` → auto-deploys to staging (`ssr-juniors-dev` Hosting). `main` → deploys to production (`ssr-juniors` Hosting), gated by a GitHub Environment (`production`) requiring manual reviewer approval.

- **PR previews (`firebase-hosting-pull-request.yml`) now force `EXPO_PUBLIC_APP_ENV=staging`.** This was the single most severe finding — every open PR previously got a live preview URL whose Firestore calls silently hit production. Fixed alongside the other two workflows, same mechanism.

- **Each environment gets its own Android package id** (`com.mercecii.schoolapp.dev` / `.staging` / unchanged `com.mercecii.schoolapp` for prod), instead of all three sharing one identity.
  **Why:** one shared package id meant a QA APK install could silently overwrite a prod install (or vice versa) on the same device, and testers couldn't tell builds apart by icon/name alone.
  **Trade-off accepted:** this requires a manual Firebase Console prerequisite (registering two new Android apps under `ssr-juniors-dev`, one per new package name, each needing its own `google-services.*.json`) before the corresponding code path is live — user chose to do this rather than defer it, given the migration is already in progress and there are no users to disrupt.

- **Firestore Security Rules will be pulled from what's actually deployed today, not written from scratch,** before being brought under version control.
  **Why:** nothing is checked into the repo currently — rules exist only in each project's console, unversioned. Starting from ground truth avoids accidentally tightening or loosening access on first deploy.

- **Rules deploys stay a manual, human-reviewed command** (`deploy-rules-dev` / `deploy-rules-prod`, mirroring the existing `functions` deploy scripts) — not wired into the auto-deploy CI workflows.
  **Why:** security rules are high-blast-radius; auto-deploying them on every push removes the review step that matters most for this particular file.

- **`app.json` replaced entirely by `app.config.ts`**, function-based, keyed off `EXPO_PUBLIC_APP_ENV`. Verified via `npx expo config --json` under all three env values plus unset: production resolves byte-for-byte identical to the old `app.json` (name, package, icon background all unchanged); staging/development get distinct names (`KPS (Staging)` / `KPS (Dev)`) and adaptive-icon background tints (no new icon artwork this pass — cheapest visual differentiator); unset defaults to `development`, never production.
  **Why byte-for-byte for prod:** the existing Play Store listing and installed base must be completely undisturbed by this migration.

- **Landed the package-id split immediately, accepting that it breaks `yarn build-e2` until the Firebase Console prerequisite is done** — `eas.json`'s `e2` profile now points at `google-services.staging.json`, which doesn't exist yet.
  **Why:** user chose "land it now" over staging the rollout behind the old package id — zero users means no build-cadence pressure, and one clear blocking TODO beats a two-step migration with a silent intermediate state.

## 2026-07-14 — Data model redesign for v2 (roles, classes, attendance, fees)

**Context:** Building out this repo into a real school app for a friend's school. Still zero live users, so the schema can be redesigned freely rather than migrated. Scope: add `teacher` and `parent` as first-class roles (today only `admin`/`student` exist), plus attendance tracking and fee tracking. Decided to extend this repo's existing Expo + Firebase stack rather than start a new project, since auth, push, and the dev/staging/prod pipeline are already solved here.

### Decided

- **Four roles going forward: `admin`, `teacher`, `parent`, `student`.** `student` is data only, never an auth identity — `parent` is the login-holding role that owns a child's data, same operating model as today's parent-phone login, just formalized as its own account instead of overloading the student doc.
  **Why:** matches how the app already works (login is by `parentPhone`, not the child's own phone) — this is a naming/structure fix, not a behavior change, for v1.

- **Separate top-level collections per role** (`admins`, `teachers`, `parents`, `students`) instead of one unified `users` collection with a `role` field.
  **Why:** matches the existing `admins`/`students` split, keeps security rules simple and isolated per role instead of one collection with conditional role-branching logic.

- **`students` and `parents` and `teachers` are auto-ID keyed, not UID-keyed** — replacing the fragile doc-ID-migration pattern used today (`ensureStudentDocUsesUid` rewrites a doc's *ID* to the auth UID via `writeBatch` on first login).
  **Why:** doc-ID migration means any reference to that doc's old ID breaks, and it structurally can't support two students sharing one parent phone (only one doc can become that UID). Instead: `parents`/`teachers` docs get a normal auto-ID at creation with a `phone` field (indexed) and a nullable `authUid` field, set (not migrated into) on first login by looking up the doc by phone. Subsequent logins query by `authUid` directly. `students` never authenticate at all in v1, so they get auto-ID with no `authUid` field, referenced by `parentUids: string[]` (student → parents) and `childStudentIds: string[]` (parent → students).
  **Also fixes:** siblings under one parent phone, which the current doc-ID-migration design can't cleanly support.

- **Teachers self-serve via OTP login, same phone-lookup-and-adopt pattern as parents** (not admin-provisioned with a known UID upfront).
  **Why:** user's explicit call. Means `teachers` and `parents` share near-identical lookup/adopt logic — implement as one shared helper parameterized by collection name, not duplicated per role. `admins` stays UID-keyed and provisioned directly (unchanged from today — admin docs are seeded manually, never self-registered, per the existing rules comment).

- **New `classes/{classId}` collection** normalizes what's currently free-text `class`/`section` fields duplicated on every student doc.
  **Why:** needed as a real entity to hang `classTeacherUid` off of and to key attendance by. Typo'd free-text class names would otherwise silently fragment attendance/roster data.
  **v1 simplification, called out explicitly:** a student has one *current* `classId`; no year-over-year class history is tracked yet. Revisit if promotion/year-rollover history becomes a real need.

- **Attendance: one doc per class per day**, `attendance/{classId}_{date}`, holding a `records: map<studentId, status>` map — not a per-student subcollection.
  **Why:** matches the chosen v1 granularity (daily, per class, not per period) and how a teacher actually marks it — one write for the whole roster. **Trade-off accepted:** a single student's attendance history requires reading multiple class-day docs and filtering the map client-side; fine at single-school scale, revisit with a Cloud Function aggregation only if reporting load grows.

- **Fees: dues are materialized, not inferred.** Creating/activating a `feeStructures` doc generates one `feePayments` subdocument (status `unpaid`, `amountDue` set) per applicable student under `students/{id}/feePayments/{id}`.
  **Why:** makes "who hasn't paid Term 1" a single query instead of a computed diff against the full roster every time.
  **v1 scope: manual/offline tracking only** — admin records cash/bank/cheque payments by hand. No in-app payment gateway, no webhook/PCI surface, per user's explicit call.

- **Push token `devices` subcollections move to the three login-holding roles** (`admins/{id}/devices`, `teachers/{id}/devices`, `parents/{id}/devices`) — removed from `students`.
  **Why:** students never log in in this model, so they were never the right place for a push token. This is also the structural fix for the "prod push notifications non-functional" issue already logged above — that bug happened because push tokens were being attached to the role that doesn't actually hold the auth session.

- **`notifications` collection reused mostly as-is**, extended with `createdByRole: "admin" | "teacher"` and a `"class"` value added to `targetType`.
  **Why:** lets a teacher post to their own class, rules-scoped by `classId` in `targetValue`, without opening school-wide broadcast to non-admins.

- **New `authz/{uid}` collection, UID-keyed, to restore rules-side "who is calling" resolution lost by moving `parents`/`teachers` off UID-keying.** Fields: `role: "admin" | "teacher" | "parent"`, `profileId` (the role doc's auto-ID), and `childStudentIds` (for parents) or `classIds` (for teachers). Written/updated at phone-adoption time and whenever an admin changes a parent's/teacher's children/class assignments.
  **Why:** Firestore rules can only `get()`/`exists()` by a known path — they cannot query "which `parents` doc has `authUid == request.auth.uid`." UID-keyed collections (`admins`) get caller resolution for free from the path itself; auto-ID collections (`parents`, `teachers`) lost that the moment they stopped being UID-keyed. `authz/{uid}` restores a single, direct `get()` lookup for rules, with sync risk centralized in one doc per user rather than fanned out across every student/class doc. Considered denormalizing UIDs onto `students.parentUids` / `classes.teacherUids` instead — rejected for v1 because sync-on-removal (unassigning a child or reassigning a class) is easy to miss when spread across many docs; a single `authz` doc per user is one place to get right.

- **Attendance flips from one map-doc per class per day to one doc per student per day** (`attendance/{studentId}_{date}`), reversing the earlier "one doc per class" decision above.
  **Why:** Firestore security rules grant read access per-document, never per-map-key. The map-per-class shape meant any parent/teacher cleared to read a class's attendance doc could see *every* student's status that day, not just their own child's — unacceptable given this is minors' data. Per-student docs make each one independently rules-checkable (`isAdmin() || isTeacherOfClass(classId) || isParentOfStudent(studentId)`, resolved via `authz`). Teacher UX is unchanged: marking a class is still one batched write from the UI (~30–40 docs, trivial for Firestore), just fanned out to per-student docs instead of one map doc. `classId` and `date` are still stored as fields on each doc so the teacher's daily class view queries `attendance.where('classId','==',X).where('date','==',Y)` — same read pattern as before, just per-doc instead of per-map-key.

- **Notifications: kept as one flat `notifications` collection with targeting fields (not fanned out to one doc per recipient), but fixed the same per-document-read problem attendance had, plus a doc-shape issue carried over unexamined from the old schema.**
  **Why flat, not fan-out:** a school-wide notification stays one cheap write this way. Fan-out to one doc per recipient only pays off if read-receipt write contention becomes real (many users hitting the same doc's `readBy` concurrently) — won't happen at one small school. Revisit only if that changes.
  **Fixed 1 — `readAt`/`readReceipt` dropped from `NotificationDoc`.** Both were meaningless on a doc shared by many recipients (whose `readAt`? whose receipt?) — a leftover from the old schema that was never examined against the new multi-recipient reality. `readBy: string[]` alone answers "who's read this"; no per-user read timestamp in v1.
  **Fixed 2 — `targetType: "individual"` now targets the recipient's stable role-doc ID (`profileId`), not an auth UID.** An admin can create an individual notification for a parent who hasn't logged in yet — no `authUid` exists at send time, the same "don't key by a UID that doesn't exist yet" problem that drove the auto-ID decision in the first place. Rules resolve it via `get(authz/$(request.auth.uid)).data.profileId == resource.data.targetValue`. Since students never log in, an individual notice "about" a student is addressed to the parent's `profileId`, not the student.
  **Fixed 3 — parent `authz` docs gain a derived `classIds` field** (teacher `authz` already had one). Firestore rules can't loop `childStudentIds → get(student) → classId` to check class membership, so a parent's `authz.classIds` must be denormalized up front — same fan-out/sync mechanism already committed to for `authz`, just one more field. Class-targeted read check becomes `resource.data.targetValue in authz.classIds`.
  **Fixed 4 — the `readBy`-append update rule must repeat the same targeting predicate as the read rule.** Write rules don't inherit read scoping — a client holding a known doc ID could otherwise blind-write `arrayUnion` into `readBy` on a notification it isn't a target of. Low practical risk given Firestore auto-IDs aren't guessable, but kept symmetric on principle.
  **Noted, not blocking:** a parent/teacher's notification feed is `school-wide ∪ my class(es) ∪ individual-to-me` — three separate queries merged client-side (or an `or()` filter, capped at 30 disjunctions), not one query. Flagging so the client-side work isn't a surprise later.

- **`authz/{uid}` is `allow write: if false` in rules — never client-writable, maintained only via a Cloud Function trigger on `teachers`/`parents` doc writes.** Discovered while writing the rules themselves, not decided up front.
  **Why:** if `authz` were client-writable (even restricted to "own doc"), a signed-in user could write themselves an `authz` doc claiming `role: "admin"` or fabricate `classIds`/`childStudentIds` they don't actually have — the exact self-escalation shape as the admin self-promotion bug already fixed in this repo. The `authUid` self-adopt write on `teachers`/`parents` itself stays client-side (authorized via the verified `phone_number` token claim, restricted to only the `authUid`/`lastLoginAt`/`updatedAt` fields) — but the `authz` doc it feeds has to be derived server-side by a Cloud Function reacting to that write, using the Admin SDK, which bypasses rules entirely. Same function should also re-derive `authz.classIds`/`childStudentIds` (and the denormalized `students.parentUids` / `classes.classTeacherUid`) whenever an admin changes assignments, not just at first adoption.

- **`classes` gets a `classTeacherId` (teacher doc ID, admin-assigned, always known) separate from `classTeacherUid` (derived auth UID, synced server-side).** Discovered while building the `authz`-sync Cloud Function: an admin assigns a homeroom teacher to a class before that teacher may have ever logged in, so `classTeacherUid` can't be the field the admin writes directly — same "don't key by a UID that doesn't exist yet" shape as `students.parentUids` and `authz` itself. `classTeacherUid` is now fanned out by `syncTeacherAuthz` (see below) whenever a teacher with a matching `classTeacherId` adopts.

- **`functions/src/authzSync.ts` — the Cloud Function that maintains `authz/{uid}`, `students.parentUids`, and `classes.classTeacherUid` server-side**, triggered by `onDocumentWritten` on `teachers/{id}` and `parents/{id}`. Handles adopt (authUid null → set), reassignment (children/classes changed on an already-adopted account), and teardown (doc deleted, or authUid cleared) — not just the add case.
  **Real bug caught before deploy, not after:** the module originally called `getFirestore()` at top-of-module scope. Since it's re-exported from `functions/src/index.ts` (`export { syncTeacherAuthz, syncParentAuthz } from "./authzSync"`), ES module evaluation runs all imported modules *before* the importing module's own top-level code — meaning `authzSync.ts`'s `getFirestore()` would have executed before `index.ts`'s `initializeApp()` call regardless of where the export line sits textually in the file. That throws on every cold start. Fixed by making `db()` a lazy accessor called inside each handler instead of a module-scope constant. Verified via `tsc --noEmit`, `eslint`, and a full `npm run build` in `functions/` — all clean.

- **Emulator round-trip test (`scripts/emulator-round-trip-test.js`) caught a real rules bug that `tsc`/dry-run compilation could never have found.** The attendance read rule used the shared `isConnectedToClass()` helper, which is `true` for both teachers *and* parents (a parent's `authz.classIds` is derived from their children's classes — see notifications, where that's the *correct* behavior). Combined with CEL operator precedence (`&&` binds tighter than `||`), this meant a parent connected to a class through one child could read **any classmate's attendance in that class** — reintroducing, in the read rule itself, exactly the per-child privacy leak the whole per-student-doc redesign existed to prevent. The bug was invisible to every check run so far (rules compiled clean, `tsc` had nothing to say about it) because it's a logic error in what the rule *permits*, not a syntax or type error.
  **Fix:** attendance's read rule no longer uses `isConnectedToClass()` — it explicitly checks `isTeacher() && classId in myClassIds()` for the teacher case, keeping the parent case scoped to `isParentOfStudent()` only. `isConnectedToClass()` stays in use for notifications, where class-wide visibility for both roles is the intended behavior, not a leak.
  **Why this matters beyond the one bug:** compiling and typechecking verify the code is well-formed, not that it does what you meant. The round-trip test (seed via Admin SDK → parent phone-adopts via the client SDK → wait for the Cloud Function fan-out → assert both an allowed read and a denied read) is the only check in this whole pass that actually exercised rule *behavior* under real data. Re-run it (`firebase emulators:start --only auth,firestore,functions` then `node scripts/emulator-round-trip-test.js`) after any future change to `firestore.rules` or `functions/src/authzSync.ts`.

## 2026-07-15 — Native Firestore auth-bridge fix (crash on every teacher/parent login)

**Bug found by actually running the app** (`yarn android` + logcat), not by reading code: every Firestore read crashed immediately on launch with "Missing or insufficient permissions," for every teacher/parent, right after "Restoring session for UID." Root cause: `firebaseSetup.ts` creates the Firestore client from a plain web JS-SDK Firebase app (`firebase/app` + `firebase/firestore`), while `utils/authClient.native.ts` authenticates via `@react-native-firebase/auth`'s separate native app instance. The two share no session, so on native every Firestore call carried `request.auth == null`, and the rules require `isSignedIn()` almost everywhere. Invisible on web because `authClient.web.ts` uses `getAuth(app)` on the *same* app as Firestore.

**Fix — native-to-web session bridge:**
- New Cloud Function `functions/src/mintFirestoreToken.ts` (`onCall`): verifies the caller's native ID token (via the callable framework's automatic `request.auth`) and mints a Firebase custom token for that uid via `getAuth().createCustomToken(uid)`.
- `firebaseSetup.ts` now also exports `webAuth` (`getAuth(app)`, same app as Firestore).
- `utils/authClient.native.ts` adds `ensureFirestoreSession(user)`: calls the Cloud Function via `@react-native-firebase/functions`, then `signInWithCustomToken(webAuth, token)`. `signOut()` now signs out both the native and web sessions together — they'd otherwise drift, leaving a "signed out" app still able to read/write Firestore as the previous user.
- `utils/authClient.web.ts`'s `ensureFirestoreSession` is a no-op (web already shares one session for both).
- `app/_layout.tsx` awaits `ensureFirestoreSession(u)` before any Firestore call, inside a new try/catch around the whole session-restore flow (previously an unhandled promise rejection here left the user stuck on an infinite loading spinner instead of a real error state).

**Also fixed in the same pass, found while tracing the crash:** `firestore.rules` was missing the `authUid`-based read branch on `teachers`/`parents` that this repo's own decision above (2026-07-09 entry, `authUid` query section) already documents as the intended "subsequent login" path — the rule only ever authorized the phone-based first-adopt path. Deployed to `ssr-juniors-dev`. This wasn't the proximate cause of the crash above (the admin-doc check fails first), but would have surfaced as the same error once the auth-bridge fix let the code reach that far.

**Why the custom-token approach over switching native Firestore to `@react-native-firebase/firestore`:** the native RNFirebase Firestore SDK would share the native auth session automatically with no bridging needed at all — but it reverses the explicit "single web JS SDK client for Firestore on every platform" decision made earlier in this log specifically to avoid a prod/dev project mismatch bug. Custom-token exchange keeps that architecture intact at the cost of one extra network round-trip per login.

### Update — 2026-07-16 (Claude Code) — retried on-device, same symptom, found the real bug: a fuzzy Firestore query that's unauthorizable by rules

**After deploying rules/indexes/functions above, the user retried on the real Android device and hit the exact same `❌ Failed to restore session: FirebaseError: Missing or insufficient permissions.`** Ruled out `mintFirestoreToken` first by tailing `firebase functions:log --project ssr-juniors-dev --only mintFirestoreToken`: the invocation at the time of the failed session (16:21:56) logged `"Callable request verification passed"` with no follow-on `Unhandled error` line — i.e. it succeeded (the fix from the prior entry is confirmed live and working). Also confirmed via the same logs that the *previous* on-device attempt, at 15:09:26 (before rules/indexes/functions were deployed), had also actually succeeded at minting the token — meaning that attempt's failure really was the rules gap described in the prior entry, not this one. So the failure had to be a client-side Firestore read denied by rules, downstream of a working token mint.

**Root cause: `utils/phoneRoleAdoption.ts`'s `findByPhone()` queried `where("phone", "in", candidates)`, where `candidates` was up to 10 fuzzy-formatted variants of the auth phone number (raw, digits-only, `+91`-prefixed, last-10-digits, etc.) — intended to tolerate admin data-entry variance.** `firestore.rules`'s read rule for `teachers`/`parents` authorizes this lookup via `isPhoneOwner(resource.data.phone)`, i.e. `request.auth.token.phone_number == resource.data.phone`. Firestore's rules engine only permits a `list`-type query when it can *statically* prove every possible matching document satisfies the rule — for an equality-based rule like this, that's only provable when the query's own filter is a single `==` (or `in` with exactly one value) against the same literal the rule compares to. A 10-value `in` clause can't be proven that way (most candidate strings don't equal `request.auth.token.phone_number`), so Firestore rejected the **entire query** with `permission-denied` — unconditionally, regardless of whether a matching doc existed. This made the already-shipped `"phone-format-mismatch"` status genuinely unreachable dead code: the query always threw before that comparison logic ever ran.

**This was invisible to `scripts/emulator-round-trip-test.js`'s prior 18/18-passing run because the test never actually called `resolvePhoneLoginRole()` / `findByPhone()`** — it seeded the parent/teacher doc via the Admin SDK (which returns the real doc ID, bypassing rules entirely) and then drove the adopt step with a hand-written `updateDoc(doc(cdb, "parents", parentRef.id), ...)` straight to that known ID. The actual phone-lookup query that real login goes through was never exercised. A real, disguised blind spot in what "18/18 passing" was actually claiming.

**Fix:** `findByPhone()` now queries only `where("phone", "==", phoneNumber)` — the one shape Firestore can prove safe against `isPhoneOwner()`. The fuzzy-matching tolerance was solving a problem admin-side validation already prevents, at the cost of being fundamentally incompatible with how Firestore rules validate queries. Removed the now-dead `candidatesFor`/`normalizePhone` helpers, the unreachable `"phone-format-mismatch"` status variant and its `app/_layout.tsx` UI branch, rather than leave dead code that implies a capability that never worked.
